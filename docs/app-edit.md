# 次にすること（タスク管理アプリの修正と都度リリース）

タスク管理アプリでのAI開発サイクルを回します。以下の**4つの機能を、1機能=1ブランチ=1PR**で順番に追加し、**1機能完成するたびに本番へリリース**します（4機能まとめてではなく、都度出します。リリースの単位が小さいほど、問題が起きたときに原因を即断できます）。
どの機能も**テストとセットで完了**です。機能が正しいことはテストで担保します——テストのない実装、テストが赤いままのPRは不合格です。

## 準備（最初に1回だけ）

1. [CLAUDE.md](../CLAUDE.md) 全体を読む（以降のAI開発の全ルール）
2. タスク管理アプリの設計書一式（[docs/design/task/](./design/task/)）を読み、**各文書とコードの対応**を確認する（API一覧 ⇔ TaskController、ER図 ⇔ Flywayマイグレーション）
3. [architecture-guide.md](./architecture-guide.md) の「新機能追加のレシピ」を読む

## 進め方（4機能とも共通）

1. ブランチを切る（例: `feature/priority`）
2. Claude Code に指示する。**最初は「先にAPI設計とDB変更案を提示して。実装はまだしない」**と伝え、提示された設計を自分でレビューして、合意してから実装+テストに進ませる
3. **設計書（API一覧・ER図・テーブル定義）も同じPRで更新させる**
4. ローカルで品質チェックを実行する（`cd backend && ./mvnw verify` ／ `cd frontend && npm run lint && npm test && npm run build`）
5. PR → **CIが緑になること**を確認 → マージ
6. マージしたら、**その機能をすぐ本番へリリース**する（下の「リリース手順」）
7. 本番で動作を確認してから、次の機能のブランチへ進む

> DBの変更は必ず**新しい連番のマイグレーション**（`V2__`、`V3__`…）で行います。適用済みのVファイルの編集・削除は禁止です（[CLAUDE.md](../CLAUDE.md)）。

## リリース手順（機能をマージするたびに毎回実行）

1. ローカルで最新のmainを取得してイメージをビルドし、サーバーへ転送します

   🟧 **Ubuntu（ローカル）**

   ```bash
   git switch main && git pull
   docker compose -f docker-compose.prod.yml build
   docker save my-training-task-web:latest my-training-task-backend:latest | gzip > app-images.tar.gz
   scp -i ~/.ssh/LightsailDefaultKey-ap-northeast-1.pem app-images.tar.gz ubuntu@<静的IP>:~/
   ```

2. サーバーでイメージを取り込んで反映します

   🟩 **サーバー（Lightsail）**

   ```bash
   docker load -i app-images.tar.gz && rm app-images.tar.gz
   docker compose -f docker-compose.prod.yml up -d
   ```

3. `https://<自分のドメイン>` で**追加した機能が動くこと**を確認して、次の機能へ進みます

## 機能1: タスクの優先度

**何ができるようになるか**:
- タスクの追加時に優先度（高/中/低）を選べる。未選択なら「中」で登録される
- 一覧の各行に優先度が表示される（色付きバッジなど、見た目はAIに任せてよい）
- 一覧を優先度順（高→中→低）に並べ替えられる

**変更の範囲**:
- 画面: **追加なし**。既存の一覧画面に「追加フォームのセレクト」「各行のバッジ」「並べ替えの操作」を足すだけ
- API: タスク作成の入力・取得のレスポンスに優先度が増える
- DB: `tasks` に列追加（新しい連番のマイグレーション）

**AIと合意する設計の論点**: DBでの表現（文字列か数値か） ／ 並べ替えの実現方法（APIのクエリパラメータか、フロント側ソートか） ／ 既存タスクに入るデフォルト値

**テストで担保すること**:
- backend: 優先度を指定して作成→取得で同じ値が返る ／ 未指定で作成すると「中」になる ／ 不正な値（例: `URGENT`）は400が返る
- frontend: 一覧に優先度が表示される ／ 追加フォームで選択できる

## 機能2: タスクの期限

**何ができるようになるか**:
- タスクの追加時に期限（日付）を任意で入力できる（空のままでもよい）
- 一覧の各行に期限が表示される
- **期限切れ（今日より前かつ未完了）のタスクがひと目で分かる**（行の色やラベルで強調）

**変更の範囲**:
- 画面: **追加なし**。既存の一覧画面に「追加フォームの日付入力」「各行の期限表示と期限切れの強調」を足すだけ
- API: タスク作成の入力・取得のレスポンスに期限が増える
- DB: `tasks` に列追加

**AIと合意する設計の論点**: 日付だけ持つか時刻まで持つか ／ 期限切れ判定をフロントとAPIのどちらで行うか

**テストで担保すること**:
- backend: 期限付きで作成→取得で同じ日付が返る ／ 期限なしでも作成できる（null許容）
- frontend: 期限が表示される ／ 期限切れの未完了タスクに強調表示が付く（「今日」を固定した上で過去日・未来日を検証）

## 機能3: 完了日時の記録

**何ができるようになるか**:
- タスクを完了にすると、その瞬間の日時が**自動で**記録される
- 完了済みタスクの行に完了日時が表示される。完了を取り消すと消える

**変更の範囲**:
- 画面: **追加なし。入力欄も増えない**（ユーザーが日時を入力するのではなく、完了操作の副作用として自動で入る）。完了済みの行に日時表示が増えるだけ
- API: タスク取得のレスポンスに完了日時が増える（完了操作のリクエスト形は変えない）
- DB: `tasks` に列追加

**AIと合意する設計の論点**: 既存の完了フラグとの関係（残すか、完了日時のnull判定に一本化するか） ／ **日時はクライアントから送らせず、サーバー側で現在時刻をセットする**こと

**テストで担保すること**:
- backend: 完了にする→完了日時が入る ／ 取り消す→nullに戻る ／ 作成直後はnull
- frontend: 完了タスクに完了日時が表示される

## 機能4: カテゴリ（テーブル追加）

**何ができるようになるか**:
- カテゴリ（例: 仕事/私用/勉強）をタスクに任意で1つ付けられる
- 一覧をカテゴリで絞り込める（「すべて」+各カテゴリのセレクト）
- カテゴリ自体の追加・削除ができる

**変更の範囲**:
- 画面: **新しいページは作らない**（ページ遷移やルーターの導入は不要）。既存の一覧画面に「追加フォームのカテゴリセレクト」「絞り込みセレクト」を足し、カテゴリの追加・削除は同じ画面内の**「カテゴリ管理」欄**（小さな一覧+追加入力+削除ボタン）として設ける
- API: カテゴリ用の新しいエンドポイント（`/api/categories` の追加・一覧・削除）が増える。タスクの作成入力・取得レスポンスにカテゴリが増え、一覧取得に絞り込みの指定が増える
- DB: **新しいテーブル `categories`** + `tasks` への外部キー（null許容）。初期カテゴリはマイグレーションのシードで投入する

**AIと合意する設計の論点**: **使用中のカテゴリを削除できるか**（エラーで禁止する／タスク側を「カテゴリなし」に戻す）——決めた仕様を**そのままテストにする**

**実装の型**: backendは `task/` パッケージを手本に `category/` パッケージ（Controller/Service/Repository/Entity/dto）を複製する

**テストで担保すること**:
- backend: カテゴリの追加・一覧・削除ができる ／ カテゴリ付きでタスク作成→取得で返る ／ 存在しないカテゴリIDの指定は400 ／ **使用中カテゴリの削除が合意した仕様どおりに振る舞う**
- frontend: 追加フォームでカテゴリを選択できる ／ 絞り込みが機能する
