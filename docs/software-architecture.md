# ソフトウェアアーキテクチャ解説 — この型は「なぜ」こうなっているか

[architecture-guide.md](./architecture-guide.md) が「何をどの順で作るか(型)」を示す手順書なのに対し、本書はその型の**背景にある原則・判断基準・現場での選択肢**を解説します。
設計書を読んでいて「なぜこう分けるのか」と思ったとき、AIの提案が型から外れていて採否に迷ったときに開いてください。

## 1. アーキテクチャには2つのレベルがある

同じ「アーキテクチャ」という言葉でも、話しているレベルが違うと噛み合いません。この教材では2つを区別します。

| レベル | 問い | この教材での答え |
|---|---|---|
| システムアーキテクチャ | どんな部品(プロセス)が、どう繋がって動くか | SPA(React)+ REST API(Spring Boot)+ RDB(PostgreSQL)の3層。本番では nginx が入口になり、全てコンテナで動く |
| アプリケーションアーキテクチャ | 1つのプロセスの**中身**をどう分けるか | backend はレイヤードアーキテクチャ+機能単位パッケージ。frontend は画面(コンポーネント)とAPI呼び出しの分離 |

システム全体の図は [architecture.drawio](./architecture.drawio)、本番の部品構成は [images/release-flow.drawio.svg](./images/release-flow.drawio.svg) を参照してください。以降は主にアプリケーションアーキテクチャの話です。

## 2. レイヤードアーキテクチャの原理

### 依存は一方向にしか流れない

```
Controller → Service → Repository → Entity
```

矢印の向きは「知っていてよい方向」です。Controller は Service を呼べますが、Service は Controller を知りません。Repository は Service の存在を知りません。
この一方向性が守られていると、**変更の影響が下流に波及しない**という性質が生まれます。HTTPの都合(ステータスコード・パス)を変えても Service は無傷、テーブル構造を変えても Controller は無傷、という状態を保てます。逆流(Service が Controller に依存する等)は `ArchitectureTest`(ArchUnit)がCIで検出します。

### 各層が「持たない」責務の方が重要

層の責務は architecture-guide の表のとおりですが、実務で効くのは「**その層が持ってはいけないもの**」の意識です。

| 迷いやすい処理 | 置く層 | 理由 |
|---|---|---|
| 入力の形式チェック(必須・文字数・数値範囲) | DTO(Bean Validation) | HTTP境界での門番。Service に届く前に弾く |
| 業務ルール(在庫不足なら出庫不可、履歴ありは削除不可) | Service | 「業務として正しいか」はロジックの中心。Controller や Repository に書くと再利用もテストもできない |
| 集計・検索条件 | Repository(クエリ) | データの取り出し方の話。Service で全件取得して Java でフィルタするのは、件数が増えた瞬間に破綻する |
| HTTPステータスの決定(201/404/409) | Controller と例外ハンドラ | Service は HTTP を知らない。Service は「業務例外を投げる」まで、それを 409 に変換するのはハンドラの仕事 |
| トランザクションの開始・終了 | Service | 1つの業務操作(=Service のメソッド1回)が原子性の単位 |
| ログ出力(誰が何をしたか) | Service(業務イベント)/ Controller(アクセス) | 何を記録したいかで層が決まる |

「この処理はどの層か」に迷ったら、**「この処理はHTTPが無くても成立するか?」「DBが無くても成立するか?」**と問うと層が決まります。HTTP が無くても成立する処理は Controller に置いてはいけません。

## 3. クラスとパッケージの分け方

### 機能単位で切る(レイヤー単位で切らない)

この教材は `task/` `item/` のように**機能(ドメイン)ごと**にパッケージを切り、その中に Controller〜Entity を並べます。現場には `controller/` `service/` とレイヤーごとに切る流儀もあります。どちらも正解ですが、機能単位を選んでいる理由は**変更の局所性**です。

- 「在庫機能を直す」とき、触るファイルが1つのフォルダに集まっている(凝集度が高い)
- 新機能の追加が「フォルダを1つ複製する」作業になり、AIへの指示も「`task/` と同じ形で」の一言で済む
- 機能を丸ごと削除・切り出し(将来の分割)がしやすい

レイヤー単位の現場に配属されても、責務の分け方は同じなので読み替えは容易です。

### 1クラスの大きさの目安と、分割のサイン

「単一責任の原則」(1つのクラスが変更される理由は1つであるべき)を、実務的な目安に落とすとこうなります。

| サイン | 対処 |
|---|---|
| Service のメソッドが10個を超え、互いに無関係な業務が同居している | ユースケースの塊で Service を分ける(例: `ItemService` と `ItemImportService`) |
| 1メソッドが画面1枚分(50行超)になり、コメントで「ここから〜処理」と区切っている | private メソッドに切り出すか、別クラスに責務を移す |
| 同じ計算(現在庫の集計など)を2箇所以上に書いている | 1箇所に寄せる。Repository のクエリか、Service の1メソッドに |
| 2つの機能で本当に同じコードが必要になった | **そのとき初めて** `common/` へ。先回りで共通化しない |

この研修の課題規模(1機能あたり数百行)では、分割が必要になる場面はほぼありません。**「型を素直に繰り返す」が最適解**で、抽象化や共通基底クラスは重複が本当に痛くなってからで間に合います(architecture-guide の「なぜ共通基底クラスを作らないのか」参照)。

### 機能をまたぐとき(他機能のデータが必要なとき)

在庫管理では、入出庫(`movement/`)が品目(`item/`)の存在確認をします。機能をまたぐ参照のルールは次のとおりです。

- **読み取り**は他機能の Repository を直接呼んでよい(`MovementService` → `ItemRepository`)。レイヤーの向きは守られている
- **更新**は相手機能の Service を経由する(相手の業務ルールを飛び越えて直接書き換えない)
- 循環(A の Service が B を呼び、B の Service が A を呼ぶ)が生まれたら、設計の境界がずれているサイン。共通の下位機能に切り出すか、どちらかに寄せる

## 4. DTO と Entity を分ける理由

Entity(テーブルと1対1のクラス)をそのまま API の入出力に使えば、クラスが半分で済みます。それでも分けるのは、**APIの形とテーブルの形は違う速度で変わる**からです。

- テーブルに内部管理用の列(削除フラグ・監査列)を足しても、APIに露出させたくない
- API のレスポンスに計算値(在庫管理の `stockQuantity`)を含めたいが、テーブルにその列はない
- Entity を直接返すと、JPA の遅延ロードや双方向関連が JSON 化の事故(無限ループ・N+1)を起こす

変換の置き場所はお手本の型どおり、**Response 側の static ファクトリ**(`TaskResponse.from(entity)`)です。変換ロジックが1箇所に集まり、Controller や Service が詰め替えコードで汚れません。Request は Java の `record` で定義し、Bean Validation のアノテーションをそこに書きます(入力の契約が1ファイルで読める)。

## 5. トランザクションと整合性

トランザクション境界は Service のメソッドです。クラスに `@Transactional(readOnly = true)`、更新メソッドに `@Transactional` を付けるお手本の型は、「読み取りは軽く、更新は原子的に」を宣言しています。

在庫管理の出庫登録が良い例です。「現在庫を集計する」→「足りていれば履歴を INSERT する」の2ステップは**同一トランザクション内**で行う必要があります。分かれていると、集計と INSERT の間に別の出庫が割り込み、在庫がマイナスになりえます。

同時実行の厳密さには段階があり、要件と規模で選びます。

| 段階 | 手段 | この教材 |
|---|---|---|
| 基本 | 同一トランザクションにまとめる | **ここまで**(設計書の割り切り) |
| 排他を強める | `SELECT ... FOR UPDATE`(悲観ロック)で品目行をロック | 必要になったら検討、と設計書に明記 |
| 競合を検知する | バージョン列による楽観ロック(`@Version`) | 画面の同時編集が問題になる規模で |
| DBに守らせる | 一意制約・CHECK制約 | `quantity > 0` 等は既に採用 |

「全部を最初から厳密に」は過剰設計です。**どこまでやるかを設計書に書いて割り切る**ことが、現場で通用する設計の仕方です。

## 6. 例外の設計

例外は「業務として起こりうる失敗」と「技術的な異常」に分けます。

- 業務例外: 対象が無い(404)、業務ルール違反(409)。Service が `NotFoundException` / `ConflictException` を投げる。**利用者に伝えるメッセージ**を持つ
- 技術例外: DB接続断、想定外の `NullPointerException` など。握りつぶさず、500 としてログに残す

HTTP への変換は `GlobalExceptionHandler` の一箇所に集約します。Service に「409を返す」と書かない理由は §2 のとおりで、Service は HTTP を知らないからです。バリデーション違反(400)・JSONが解釈できない(400)・業務例外(404/409)・それ以外(500)が全て `{"message": ...}` の同じ形で返るのは、フロントが1つのエラー表示で済む=**契約の一貫性**のためです。

やってはいけないのは `catch (Exception e) {}` で例外を握りつぶすことと、例外をフロー制御(正常系の分岐)に使うことです。

## 7. 永続化とスキーマの進化

- **スキーマ変更は前進のみ**(Flyway の連番マイグレーション)。適用済みファイルを直さない理由は、全環境(ローカル・テスト用H2・本番)が同じ履歴を再生して同じ形に辿り着くため
- **Entity とマイグレーションの二重管理**は意図的です。`ddl-auto: validate` にしてあるのは「Hibernate に勝手にテーブルを作らせない」ためで、スキーマを変えられるのは Flyway だけ、という一本化が事故を防ぎます
- **H2互換のDDL**で書くのは、テストを本物のPostgreSQLなしで高速に回すため。互換性の代償として使える構文が少し狭まりますが、その制約はCIで即座に分かります

## 8. フロントエンドのアーキテクチャ

フロントにも backend と同じ「層」の考え方があります。

| 層 | 場所 | 役割 |
|---|---|---|
| 画面(コンポーネント) | `src/components/` | 表示と操作。1ファイル1コンポーネント |
| 状態とオーケストレーション | `App.tsx` | どのデータをいつ取りに行くか。子に props で配る |
| API呼び出し | `src/api/*.ts` | fetch の集約。コンポーネントから直接 fetch しない |
| 型(契約) | `src/api/types.ts` | backend の Response/Request と対になる形 |

**コンポーネントを分ける基準**は、(1) 同じ見た目を2箇所で使う、(2) 1ファイルが読み切れない長さになる、(3) 独立してテストしたい——のいずれかです。先回りで細かく割る必要はありません。
**状態の置き場所**は「それを使う最も近い共通の親」です。入力欄の下書きはそのコンポーネント内に、一覧データは `App.tsx` に、という具合に、必要になったら上に持ち上げます(リフトアップ)。

API 呼び出しを相対パス `/api/...` に固定しているのは、開発時は Vite の proxy が、本番は nginx が backend へ転送するからです。フロントのコードが環境を知らなくて済む——これも「環境差は外側で吸収する」という同じ原則です。

## 9. テストとアーキテクチャの関係

層が分かれていると、層ごとに**テストの粒度**を選べます。この教材が APIテスト(`MockMvc` + H2)を主役にしているのは、Controller〜DB までを1本で通せて、業務ルールの検証(在庫不足なら409)と契約の検証(JSONの形)が同時にできるからです。

- ArchUnit は「構造」をテストします。依存方向が逆流した瞬間に落ちるので、レビューで目視する必要がなくなります
- フロントのテストは fetch をモックし、「画面がAPIの結果をどう表示するか」に集中します。backend を起動せずに回せるのは、API 呼び出しが `src/api/` に分離されているからです

テストが書きにくいと感じたら、それは設計のサインです(Controller にロジックがある、Service が HTTP に依存している等)。

## 10. 本番アーキテクチャとの対応

本番ではコンテナが3つ(web=nginx / backend / db)動きます。コードの層構造と本番の部品構成は別物ですが、繋がっている原則があります。

- **設定は環境変数で外から注入する**(`DOMAIN`、`DB_PASSWORD`)。同じイメージを全員・全課題で使い回せるのはこのため(いわゆる 12-factor の Config)
- **ビルドとデプロイを分離する**。成果物(イメージ)を作る場所と動かす場所を分け、サーバーにはソースコードを置かない
- **状態を持つのは db だけ**。web と backend は消して作り直せる(ステートレス)。サーバーを掃除して次の課題に移れるのはこの性質のおかげ

## 11. この型の先にあるもの(発展)

- **オニオン / ヘキサゴナル / クリーンアーキテクチャ**: 「依存を一方向に保つ」原則を、"ドメイン(業務ルール)を中心に置き、DB や Web を外側に追いやる"形に発展させたものです。レイヤードとの違いは矢印の向きの取り方で、原則は同じです
- **CQRS・イベント駆動**: 読み取りと更新でモデルを分ける、状態変化を「出来事」として記録する。在庫管理の「履歴から現在庫を集計する」設計は、実はイベントソーシング的な発想の入口です
- **マイクロサービス**: 機能単位パッケージを別プロセスに分けたもの。「まずモノリスの中で境界を正しく引く」ことができないと、分けても壊れます。この教材の機能単位パッケージは、その境界を引く練習でもあります

## 12. AIと協働するときのアーキテクチャの使い方

型が揃っていることは、人間の読みやすさ以上に**AIの生成品質**に効きます。お手本と同じ構造が1つあれば、AIは「同じ形で」という指示だけで高い精度で複製できるからです。

AIの提案を受け取ったら、次の観点でレビューしてください。

- 依存の向きは守られているか(Service が HTTP を知っていないか、Controller にロジックがないか)
- Entity が API に露出していないか
- 業務ルールは Service にあるか(フロントだけでチェックしていないか)
- 新しい層・新しい抽象(BaseXxx、Util)を**勝手に増やしていないか**——増やす提案には理由を説明させる
- 設計書(03/04)と一致しているか。違うなら「なぜ違うか」を説明させ、納得できなければ設計書に合わせる

AIは「もっともらしい構造」を提案するのが得意ですが、その構造が**このリポジトリの型と整合しているか**を判断できるのは、型を理解している人間だけです。
